# Scene Observability Implementation

This document describes the current runtime scene observability that is implemented in `manyforge`.

It is intentionally narrower than a final production observability spec. The goal of this pass is to make backend scene state and HMI scene reconciliation inspectable enough to diagnose scene drift, attach/detach errors, and render/backend mismatches.

## Included

The current implementation includes:

- Backend scene mutation trace for:
  - `add`
  - `remove`
  - `update_pose`
  - `attach`
  - `detach`
- The trace is available for:
  - native RoboPlan backend
  - Python mock backend
- HMI-side scene trace for:
  - invalidation hints reaching the HMI server
  - per-object reconciliation against backend state
  - chosen query frame
  - chosen Viser parent frame path
  - chosen render node name
  - render action outcome for state-changing reconciliations (`rendered`, `updated_pose`, `remove`, `noop`)
  - scene-node presence checks in the server-side Viser scene graph
- Composer debug API:
  - `GET /api/debug/scene-trace`
  - returns backend trace, HMI trace, and current per-object render diagnostics
- Bounded in-memory retention:
  - backend trace buffer
  - HMI trace buffer

## Excluded

The current implementation does not include:

- Browser/client-side rendering telemetry
  - no WebGL/pixel/framebuffer observability
  - no browser-side Viser client event log
- Persistent trace storage
  - traces are in-memory only
  - they are not yet written to file or external telemetry sinks
- Full planner/collision observability
  - scene mutation results are included
  - planner internals and collision-check reasoning are not
- Full robot telemetry observability
  - execution snapshots already exist for joint state
  - this document only covers scene/object observability
- Full query tracing for every backend consumer
  - backend scene queries are captured indirectly through HMI reconciliation logs
  - there is not yet a general-purpose trace for every `get_object_pose()`/`get_object_state()` call in all callers
- Spec-level guarantees
  - field names and endpoint shape are implementation details for now
  - they still need to be formalized in `manyforge_specs`

## Trace Sources

### Backend trace

Backend trace entries are exposed through:

- `KernelClient.get_scene_trace(limit=None)`
- `KernelClient.clear_scene_trace()`

For the native backend, entries are produced in the RoboPlan planning context when scene mutations are applied.

For the mock backend, entries are produced in the Python mock kernel when scene mutations are simulated.

### HMI trace

HMI trace entries are exposed through:

- `ViserHmiServer.get_scene_trace(limit=None)`
- `ViserHmiServer.clear_scene_trace()`
- `ViserHmiServer.get_object_render_diagnostics(object_id)`

These entries are generated by the server-side Viser HMI reconciliation loop.

The HMI trace intentionally omits no-op `unchanged` render reconciliations to keep the buffer focused on state transitions instead of poll noise.

## Intentional Simplifications

This pass keeps the existing callback path as an invalidation hint only.

That means:

- `scene_edit_callback` is not treated as authoritative scene truth
- `_scene_sync_requested` was removed because it was redundant
- the HMI still reconciles from backend state on the update loop
- the callback now exists only to leave a traceable invalidation breadcrumb

## How To Use It

For live debugging:

1. Reproduce the scene issue.
2. Query `GET /api/debug/scene-trace`.
3. Compare:
   - backend scene mutation events
   - HMI reconciliation events
   - current per-object diagnostics

If backend state is correct and HMI render state is wrong, the fault is in reconciliation/rendering.

If backend state itself is wrong, the fault is in scene mutation or backend state ownership.

## Required Future Traceability Scope

This implementation only covers scene/object observability.

For an industrial robotics application, traceability must be expanded to every sensitive runtime element, not only the scene. The system should make it possible to reconstruct what happened across core execution, planning, orchestration, UI/HMI, and external integration boundaries.

The sections below describe what should eventually be traceable and at what level.

### 1. Core execution kernel

Useful to trace:

- state transitions
  - `idle -> validating -> executing -> paused/stopped/completed/failed`
- command intake
  - `run`
  - `stop`
  - `reset`
  - `pause`
  - `resume`
- validation outcomes
  - start-state checks
  - goal compatibility checks
  - collision validation
  - limits / TCP-speed validation
- execution lifecycle
  - execution start
  - progress snapshots
  - completion
  - timeout
  - failure reason
- scheduler/timer activity that affects lifecycle behavior
- collision-monitor decisions during execution

Recommended level:

- structured event trace
- monotonic timestamps
- sequence numbers
- correlation ids such as `execution_id`, `move_id`, and `program_run_id`
- error codes and reason fields

### 2. Planning backend

Useful to trace:

- plan request input summary
  - motion type
  - target reference type
  - tolerances
  - timeouts
  - velocity scaling
- reference resolution
  - resolved world pose
  - source reference frame/object
- planner result
  - success/failure
  - failure reason
  - planning duration
  - trajectory duration / waypoint count summary
- retiming / constraint application
- backend scene query results used by planning

Recommended level:

- structured event trace for request/response boundaries
- optional sampled debug trace for expensive inner planning diagnostics
- summary metrics for latency and failure categories

### 3. Runtime scene / object state

Useful to trace:

- object lifecycle
  - add
  - remove
  - update pose
  - attach
  - detach
- frame ownership changes
- pose in parent frame
- resolved pose in world frame
- query path used by runtime consumers

Recommended level:

- this is the part implemented today
- keep bounded structured traces and per-object diagnostics

### 4. Behavior tree / orchestration layer

Useful to trace:

- tree lifecycle
  - tree build
  - tree reset
  - tree destruction
- node lifecycle
  - tick start
  - tick result
  - status transition
  - halt/interrupt
  - exception/failure
- node inputs/outputs at boundary level
  - request ids
  - referenced blackboard keys
  - external action result summaries
- long-running action node progress
- recovery / retry behavior

Recommended level:

- per-node structured trace, not full verbose blackboard dumps on every tick
- node status transitions should be traceable with timestamps and run correlation ids
- failures/exceptions must always be logged with node id/name/type

### 5. Blackboard / shared state

Useful to trace:

- writes to authoritative or safety-relevant keys
- key ownership/source
- last update timestamp
- invalidation/refresh of cached derived values

Recommended level:

- do not log every trivial key access
- trace writes and ownership changes for keys that influence execution, planning, or HMI
- avoid treating blackboard caches as silent state

### 6. HMI / frontend reconciliation

Useful to trace:

- backend snapshot sequence consumed by the HMI
- chosen parent frame path
- chosen render node name
- render action taken
  - rendered
  - updated_pose
  - removed
- visible status source
  - backend-derived
  - supervisory/orchestration-derived
- websocket connection state and staleness

Recommended level:

- structured reconciliation events on the server side
- optional client/browser telemetry later for browser-only rendering issues

### 7. API and supervisory plane

Useful to trace:

- incoming API commands
- command acceptance/rejection
- request/response latency
- websocket state broadcasts
- state-hub lag or dropped/coalesced updates

Recommended level:

- structured API access/events
- correlation with execution and program-run ids

### 8. External integration boundaries

Useful to trace:

- real robot controller command dispatch
- controller feedback receipt
- gripper I/O
- fieldbus/ROS/external service boundary failures
- mismatches between commanded and observed robot state

Recommended level:

- command/feedback trace at the integration boundary
- timestamps from both ManyForge and the external system when available

### 9. Metrics and health signals

Useful to trace or expose as metrics:

- queue depths
- dropped/coalesced events
- observer lag
- tick-loop period and jitter
- planning latency
- execution latency
- HMI update latency
- websocket reconnects / stale periods

Recommended level:

- metrics for trends
- event trace for anomalies and failures

### 10. Failure-focused minimum bar

At minimum, every production-sensitive failure should allow an operator or engineer to answer:

- what command was issued
- what component received it
- what state the component was in before and after
- what input data/reference it used
- what external/backend result it got
- what error code or reason was produced
- what the user/HMI was showing at the same time

If any of those questions cannot be answered from retained traces and metrics, observability is still incomplete.

When this is formalized in `manyforge_specs`, the main open decisions are:

- whether trace schemas become contractual DTOs
- whether trace retention/export becomes a required capability
- whether backend query tracing must be generalized beyond HMI reconciliation
- whether browser/client observability becomes part of the supported diagnostic model
